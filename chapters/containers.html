Chapter 18 · Packaging is not the whole deployment

18. Production-minded Docker integration

A binary works on the laptop and fails immediately in its container: “No such file or directory.” The file is visibly present. Is Docker unable to find it? Perhaps the kernel cannot find the binary’s dynamic loader. A container bundles a userspace environment, not a magical compatibility layer. Producing a deployable Odin application means accounting for that environment, its privileges, lifecycle, network, and failure behavior.

This chapter has two separate goals: package an Odin application for execution inside a container, and use Odin to invoke Docker from a host tool. Do not confuse them. An application inside a container usually does not need the Docker client or socket. A host-side Docker integration can acquire substantial control over the host and requires a much narrower authorization boundary.

Evidence boundary. The read-only Odin companion and its state-parser tests can run without starting a container. The Docker recipes are deployment procedures to validate on an explicitly selected disposable daemon. They are not a claim that image builds, networking, security isolation, or shutdown behavior were tested on this machine.

1. Define the artifact and runtime contracts first

Specify the target OS, CPU architecture, compiler revision, optimization/debug settings, native library versions, and supported inputs. Record the build command and dependency evidence in CI. A compiler version string is useful, but a release artifact also needs provenance: source revision, dependency versions, artifact digest, and the image digest actually deployed.

An Odin executable may be dynamically linked. FFmpeg or libcurl bindings add native runtime dependencies. A scratch image has no dynamic loader, C library, certificate bundle, timezone database, or shell by default. Copying one executable into scratch is valid only when its runtime requirements have actually been satisfied—not because Odin compiled it successfully.

# Inspect your own trusted build artifact, not an arbitrary downloaded executable.
file ./app
readelf -l ./app
readelf -d ./app

Check interpreter, architecture, required shared libraries, and ABI compatibility. A build on a newer glibc host can produce an executable that will not run on an older base. Compile in the approved target-compatible build environment rather than patching loader paths until a smoke test happens to pass. For an untrusted artifact, prefer static inspection to executing it or using a tool whose analysis can execute it.

2. Reproducible image inputs are more than a familiar tag

A tag can move. Select an approved base image by digest and platform, and make native-package installation reproducible through your organization’s pinned repository/snapshot policy. A digest makes the selected image immutable; it does not certify that the image is secure or that future vulnerability fixes will arrive automatically.

Use a multi-stage build when the compiler and headers should not remain in the runtime image. Keep Odin and development libraries in the build stage; copy the executable and only the required runtime material into the runtime stage. Alternatively, build the binary in a controlled CI environment and use a runtime-only image recipe. Choose one clearly rather than combining an uncontrolled host binary with an unrelated minimal base.

The following is a runtime-only template, not a complete pinned build. The build context must contain an app compiled for the selected runtime ABI. RUNTIME_IMAGE must be supplied as an approved, digest-pinned reference with any required runtime libraries already present.

# syntax=docker/dockerfile:1
ARG RUNTIME_IMAGE
FROM ${RUNTIME_IMAGE}
WORKDIR /app
COPY --chown=10001:10001 --chmod=0555 app /app/app
USER 10001:10001
ENTRYPOINT ["/app/app"]

A numeric non-root user need not have a passwd entry, but code that looks up a username or home directory may require additional runtime configuration. Test that behavior. Choose an application-owned writable path rather than granting write permission to the whole image.

Keep build contexts small with a .dockerignore allowlist appropriate to the recipe. Never copy credentials into an image layer and “delete them later”: the earlier layer may retain them. Build-time credentials belong in the builder’s supported secret mechanism, not build arguments. Scan the produced image, generate the required dependency inventory, and record its digest before release.

3. Treat the container as a separate filesystem boundary

The Docker client, Docker daemon, and container may run on three different machines. A bind mount’s source path is resolved on the daemon host, not necessarily where Odin’s Docker client is running. A directory existing locally therefore does not prove a remote daemon can mount it.

The container sees the mount target, not the host’s original path. With --mount type=bind,src=/approved/input,dst=/input,readonly, pass /input/file.wav to the application. A read-only input mount prevents writes through that mount but does not make malformed media safe to parse.

Use explicit mount declarations and validate existence, ownership, permissions, and allowed roots. Symlinks and path replacement can invalidate a check performed earlier; a string prefix is not a secure containment test. Relative paths, remote daemons, and automatic directory creation produce especially confusing failures. Docker’s --mount behavior differs from some -v convenience behavior when the source is missing.

For outputs, choose a job-owned directory or volume with the correct UID/GID permissions. Write an incomplete artifact separately, close it successfully, verify it, and publish it under an explicit policy. A writable mount exposes a host path to whatever privileges the container process has. Never grant broad host filesystem access merely to simplify an output path.

4. Limit privileges and resources deliberately

A sensible Linux baseline includes a non-root UID, read-only root filesystem, dropped capabilities, no-new-privileges, a bounded writable temporary area, and memory/CPU/PID limits. Keep the default security profile unless a verified application requirement calls for a narrow exception. These controls are layers, not proof that every hostile input is harmless.

# Illustration only: replace the placeholder with a verified image digest first.
# Verify context "default" points to your approved disposable local daemon.
docker --context default run --rm --name odin-book-lab \
  --init --user 10001:10001 --read-only \
  --cap-drop=ALL --security-opt=no-new-privileges \
  --memory=256m --memory-swap=256m --cpus=1 --pids-limit=64 \
  --tmpfs /tmp:rw,nosuid,nodev,noexec,size=16m \
  --network=none --pull=never \
  APPROVED_IMAGE_AT_DIGEST

This is a non-networked batch profile. The placeholder is intentionally not a runnable image reference. Resource values are examples to measure against your workload, not universal production defaults. In particular, FFmpeg may create codec threads and require substantially more memory than a small text tool; a limit that causes every legitimate job to fail is not a useful safety policy.

--memory-swap is a combined memory-plus-swap allowance, not an independent extra-memory setting. Whether a control is available/enforced depends on daemon mode, kernel and cgroup support. Read the host’s effective configuration and test enforcement instead of assuming a flag’s presence proves it worked.

Do not use --privileged, host networking, the host PID namespace, or a Docker-socket mount as a troubleshooting shortcut. A rootful Docker daemon can launch containers with host access. A read-only socket mount does not turn Docker API calls into read-only operations. Rootless operation can reduce some risks but is a different operational profile with its own constraints.

5. PID 1, signals, and Odin cleanup

Use an exec-form entrypoint so the intended executable is not hidden behind a shell that swallows signals. A container’s initial process has special PID-1 behavior; an init process such as Docker’s --init can forward signals and reap orphaned children. It does not implement your application’s graceful shutdown.

On termination, stop admitting work, mark readiness false, signal workers through a safe application mechanism, and finish or abort active work within a budget. Perform cleanup in ordinary control flow, not inside an asynchronous signal handler that calls allocation, logging, or codec APIs. Then exit. Test both the graceful path and what happens when the grace period expires.

Odin defer runs when its scope exits normally. It does not guarantee execution after SIGKILL, a process crash, or an OOM kill. Calling os.exit from inside an owning helper also bypasses that helper’s deferred cleanup. Return a status from the helper, then exit at the top-level boundary.

For a service, a stop-timeout must fit the actual shutdown budget. For a media batch worker, cancellation must leave a distinguishable incomplete output and enough information to reconcile the job. Do not promise that the container will always run a cleanup callback before it disappears.

6. Container loopback is not host loopback

127.0.0.1 inside a container names that container’s own network namespace. It does not name the host’s loopback service or another container. Containers on an appropriate user-defined network can use service/container DNS names; the host can reach a published port under the configured routing policy.

A service intended to receive forwarded connections normally binds an appropriate container interface, often 0.0.0.0, not only its internal loopback. Host-side publication is a separate decision. EXPOSE documents a port; it does not publish it.

# Separate networking illustration for an approved server image listening on 8080:
docker --context default run --rm --name odin-book-lab \
  --pull=never -p 127.0.0.1:18080:8080 APPROVED_SERVER_IMAGE_AT_DIGEST

Publishing without an explicit host address generally exposes the port on all host interfaces. A loopback-bound mapping is the safer local teaching choice, but the Docker documentation notes that versions before 28.0.0 could expose localhost-published ports to peers on the same layer-2 network. Check your actual daemon version and routing/firewall policy. “Localhost” is not a reason to skip verification.

Use the networking chapter’s HTTP client from the host against the published local port. From another container, use the intended service name and container port. A remote Docker daemon publishes on the remote host, not automatically on the laptop running Odin.

7. Running is not ready, and health is not a restart policy

A container can be running before its service accepts useful requests. Separate lifecycle state from application readiness. A readiness probe should verify the capability needed by callers, have a short deadline, and avoid expensive or destructive operations. A liveness probe asks a different question: can this process recover without restart?

Docker health status is distinct from lifecycle status, and an unhealthy result does not by itself implement the replacement behavior of a higher-level scheduler. Do not infer readiness from docker inspect returning running. A dependency outage may justify rejecting work temporarily rather than repeatedly killing a healthy process.

Define startup grace, probe intervals, failure thresholds, and how load balancers or job dispatchers react. Test that a failed dependency does not create a restart storm and that recovery restores readiness without accepting work too early.

8. Odin invokes the client, not a shell-shaped policy engine

The read-only companion targets only odin-book-lab and defaults to a dry run. Passing --execute is an explicit local opt-in after verifying the Docker context. It uses absolute Linux executable paths, an argument vector, a narrow inspect format, a GNU timeout wrapper, and a known lifecycle-state parser.

// Excerpt; the complete program releases stdout and stderr on every return.
"/usr/bin/timeout", "--signal=TERM", "--kill-after=1s", "5s",
"/usr/bin/docker", "--context", "default", "inspect",
"--format", "{{.State.Status}}", LAB_NAME

No shell expands those strings. That prevents shell injection, but Docker still interprets its own options and acts with the chosen daemon’s authority. Never let an untrusted request supply arbitrary Docker arguments, image references, mounts, executable paths, or contexts. Keep the operation itself narrow and authorized.

Check the Odin process-management error first, then child success/exit status, then validate the requested data. A timeout must remain a timeout, not an empty successful inspection. The companion’s narrow formatted stdout should be tiny; its post-capture size check detects an unexpected result but is not a hard bound on hostile stderr or peak capture memory.

For production operations with potentially unlimited output, use streaming process APIs and consume both pipes concurrently, keeping a bounded diagnostic tail. Otherwise the child can block on a full pipe, or the caller can exhaust memory collecting logs. Alternatively, use a maintained Docker Engine API client when typed requests, events, and richer cancellation justify it. Do not write an engine transport layer merely to inspect one fixed lab container.

9. A client deadline does not cancel a remote operation

Killing a timed-out Docker client does not prove a daemon-side create, start, build, or exec stopped. The connection can fail after the daemon accepted the action. Retrying blindly can create duplicate jobs, containers, or outputs.

For mutation-capable integrations, establish a job identity before submission and attach ownership labels to created resources. Record intent durably, reconcile the actual daemon result after an ambiguous failure, and remove only resources proven to belong to that job. A name match alone is not proof of ownership. Prefer exact recorded resource IDs, supplemented by validated labels and an explicit retention policy.

Do not automatically run broad prune commands or remove every object matching a convenient prefix. A retry policy must distinguish “not submitted,” “accepted but result unknown,” and “completed with failure.” An operator needs that distinction to recover safely after a process restart.

10. Interpret exit codes without flattening the layers

For docker run, the documented special codes are 125 for Docker invocation/daemon failure, 126 for a contained command that cannot be invoked, and 127 for a missing contained command. Other results reflect the contained command’s status under that interface. A timeout wrapper adds its own codes; do not describe its timeout as an application result.

Those conventions are specific to the command involved. The inspect companion does not apply docker run mappings to every Docker subcommand. A missing container, inaccessible daemon, failed JSON/schema expectation, and failed application are separate errors.

A shell convention such as 137 suggests termination by signal 9 but does not alone prove an OOM kill. Correlate container state, OOM information, daemon events, and host evidence. Preserve diagnostics without exposing secrets or dumping unlimited logs.

11. Secrets, logging, and observable failure

Use the deployment platform’s secret mechanism and grant only the needed readers access. Environment variables are convenient configuration but can be visible through process/container inspection and diagnostics. Do not place credentials in image layers, command-line arguments, labels, or media URLs. Separate public configuration from secrets in both code and documentation.

Write structured, bounded diagnostic events to stderr and keep application data on stdout. Record job identity, operation, duration, outcome, retry count, and resource-budget failures. Rotate/limit container logs using the approved logging driver and storage policy; application output can otherwise fill the daemon host’s disk.

Distinguish caller-visible error messages from operator diagnostics. A safe caller message need not contain a private mount path or entire external-tool stderr. Expose enough information to act without reproducing every byte an untrusted dependency supplied.

12. A release checklist that has evidence behind it

  1. Build in the approved target environment; record compiler/native-library versions, source revision, artifact and image digests.
  2. Verify architecture/loader/dependencies and scan the final image; explain each included runtime dependency.
  3. Run as the intended non-root UID with read-only root and minimum mounts/capabilities; verify permissions and secret access.
  4. Measure memory, CPU, PID, temporary-storage and log growth on representative and hostile inputs; test enforcement.
  5. Test startup, readiness, graceful stop, forced kill, dependency outage, client timeout, and daemon unavailability.
  6. Verify the actual network exposure from allowed and disallowed locations, using the selected daemon’s version/policy.
  7. Check partial-output handling, duplicate submission reconciliation, job ownership, and cleanup after restart.
  8. Document rollout, rollback, retained artifacts, operator diagnostics, and the exact unsupported cases.

A green smoke test checks one path. Production readiness is the set of these requirements for the actual service and environment, with recorded results. The book provides the design and runnable boundaries; it does not substitute a universal image recipe for that evidence.

Companion exercises

Exercise 18.1 · Inspect without changing anything. Run the default dry-run companion and its tests. Review the exact arguments, state parser, timeout classification, buffer ownership, and remaining capture limitation. Do not enable execution until you have selected an approved disposable daemon and created the named lab resource yourself.
Exercise 18.2 · Prove the runtime contract. Use a known, non-sensitive Odin binary and an approved digest-pinned runtime base. Test the intended UID, read-only root, necessary temporary directory, missing library, and wrong architecture. Expected result: each incompatibility has a distinguishable diagnosis; adding root privileges is not the fix.
Exercise 18.3 · Failure before cleanup. In the disposable environment, cancel a job mid-output and force-stop a second job. Verify neither partial file is published as successful. Record which resource IDs your job created and show that recovery never removes another job’s resource.
Exercise 18.4 · Readiness is a separate result. Run an approved local service image, publish only to loopback, and probe it with Chapter 17’s HTTP client. Compare container lifecycle state with readiness during startup and a dependency failure. Document what was tested, including daemon version, rather than claiming all container networks behave alike.
Checkpoint. Before delivery, identify the image and ABI, allowed daemon and privileges, filesystem/network boundaries, secrets, resource budgets, shutdown contract, reconciliation strategy, and proof that failed work is never published as complete.
